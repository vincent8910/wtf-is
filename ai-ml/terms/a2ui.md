# A2UI（Agent-to-User Interface，代理對使用者介面）— 讓 Agent 回傳可互動畫面，不只一段文字

> **白話說：** A2UI 像一份「畫面菜單」：Agent 說明需要哪些欄位、按鈕或圖表，由使用者的 App 用自己的原生元件畫出來；Agent 不直接傳一段可執行的畫面程式碼。

---

## 它到底是什麼？

**A2UI** 是一種讓 AI Agent 描述互動式介面的開放協定。Agent 可以回傳結構化的介面資料，例如確認表單、商品比較卡或圖表；接收端再依照自身平台與元件庫，把資料呈現成原生畫面。這樣使用者就能直接修改欄位、選項或確認計畫，不必只靠文字來回溝通。

Google 於 **2026 年 11 月 11 日**發布 **A2UI 1.0**，並稱其為首個穩定版本；官方說明當時提供 Web、Android、iOS 的 renderer SDK，以及 Python、TypeScript、Dart 的 agent SDK。官方亦指出 Jetpack Compose renderer 當時支援 0.9.1，1.0 尚在開發。這是 A2UI 專案的版本狀態，不代表它已成為所有平台共同採用的正式標準。

A2UI 的重點是「Agent 描述要呈現什麼，應用程式決定如何畫」。因此，接收端可以使用自己核准的原生元件，而不必執行 Agent 傳來的任意 UI 程式碼。這有助於跨裝置呈現與安全控管，但應用程式仍須驗證輸入、限制可用元件與操作，不能把結構化資料自動視為可信。

它和 [A2A](a2a.md) 名稱相近但用途不同：A2A 著重 Agent 彼此通訊；A2UI 著重 Agent 如何把互動介面交給使用者的應用程式呈現。它也不同於 [MCP](mcp.md)：MCP 主要規範模型與工具／資料來源如何連接，不是用來描述使用者畫面的協定。

## 生活比喻 / 實際例子

想像餐廳助理不只用口頭報菜名，而是送來一張可以勾選的菜單：助理提供菜色與選項，餐廳的平板決定按鈕長什麼樣。不同店家的平板可以長得不同，但都能讓客人完成選擇。

例如你請 Agent 安排出差，它可以顯示日期、航班和預算的確認卡片；你直接改日期、選航班並按確認，Agent 再依照結果繼續處理。實際能做哪些操作，仍由 App 的權限和元件白名單限制。

**造句：**

- 「這個流程要讓使用者直接確認選項，可以評估用 A2UI 呈現互動卡片。」
- 「A2UI 負責描述畫面內容，App 仍要自行決定允許哪些元件和操作。」
- 「不要把 A2UI 和 A2A 混為一談：一個面向使用者介面，一個面向 Agent 間協作。」

## 為什麼要知道這個詞？

- 複雜選擇、表單與比較結果，互動畫面通常比長篇文字更容易操作
- 由接收端用核准元件渲染，可維持不同平台的原生體驗與控制權
- 結構化介面資料仍可能帶有錯誤或不安全內容，接收端要做驗證與權限限制
- A2UI 是獨立協定，不能取代工具連接用的 MCP，也不能取代 Agent 間通訊用的 A2A
