# Context Compaction（上下文壓縮）— 把過長的工作紀錄整理成可繼續的狀態

> **白話說：** Context Compaction 是在 AI 的上下文快要裝滿時，把已完成的細節、重要決策、目前狀態與未完成工作整理成較短的版本，讓任務可以繼續，而不是直接忘記前面發生的事。

---

## 它到底是什麼？

AI 的 [Context Window](context-window.md) 有容量上限。長時間對話、Coding Agent 或多步驟工作會逐漸累積：

- 使用者需求與限制
- 已完成的修改
- 工具呼叫與輸出
- 錯誤與重試紀錄
- 目前決策與未完成項目

Context Compaction 會將這些內容重新整理，保留對下一步仍有用的資訊，捨棄已不再需要的冗長細節。

理想的壓縮結果至少要保留：

- 任務目標與驗收條件
- 已完成與未完成的工作
- 重要決策、限制與權限邊界
- 目前檔案／資料狀態
- 錯誤、風險與下一個建議動作

## 生活比喻 / 實際例子

像把三小時會議逐字稿整理成一份交接紀錄：不需要保留每一句閒聊，但下一位同事必須知道決議、負責人、截止時間、目前進度與尚未解決的問題。

```text
長對話／長任務
      ↓ 接近上下文上限
保留目標、狀態、決策、風險與下一步
      ↓
刪除或壓縮已完成的細節
      ↓
Agent 繼續執行任務
```

## 它和相近概念有什麼不同？

| 概念 | 解決的問題 | 簡單比喻 |
|---|---|---|
| Context Window | 一次最多能放多少資訊 | 桌子的大小 |
| Context Engineering | 準備哪些資料給 AI 使用 | 整理會議資料夾 |
| Context Compaction | 上下文太多時如何整理並延續 | 把逐字稿整理成交接紀錄 |
| Memory | 把值得長期保留的資訊存起來 | 公司的知識庫 |
| 摘要 | 將一段內容縮短 | 會議摘要 |

Context Compaction 不等於單純截斷最早的訊息，也不保證壓縮後每個細節都能恢復。對高風險任務，應保留 checkpoint、原始紀錄或可回查的工具輸出。

## 為什麼要知道這個詞？

長時程 Agent 若只依賴不斷累積的對話，很容易遇到：

- 早期限制被遺忘
- 已完成的工作被重做
- 錯誤狀態在壓縮後消失
- Agent 失去目前任務方向
- 使用者以為 Agent 還記得，但實際上下文已被整理

因此 Context Compaction 應搭配 [AI Harness](../../software-engineering/terms/ai-harness.md)、Agent evaluation、checkpoint、權限邊界與人工驗收一起設計。
